# Live Chat Palette — v1.0 Design

**Target:** Google Chrome  
**Extension Platform:** Manifest V3  
**Version:** v1.0  
**Created:** 2026-08-23  
**Updated:** 2026-08-23

## 1. Overview

Live Chat Palette is a Chrome extension that improves YouTube Live chat participation by adding a compact palette near the native chat input.

The extension provides quick access to:

- Frequently used message presets
- Channel-specific message presets
- YouTube channel custom/member emojis available to the current user
- Favorite custom/member emojis

The extension does **not** post through the YouTube Data API. Instead, it acts as a UI-assistance layer on top of YouTube's existing Live Chat input, emoji picker, and send flow.

The core v1.0 goal is:

> Add channel-aware favorite custom emojis and message presets to YouTube Live Chat so users can participate quickly without introducing unsafe automation or accidental posting.

---

## 2. Product Goals

YouTube Live viewers often repeat the same messages and channel-specific member emojis during a stream. Today this usually requires repeatedly opening the native emoji picker, locating the desired emoji, typing common messages, and then submitting them.

Live Chat Palette shortens that flow to a small number of explicit user actions.

Primary use cases include:

- VTuber streams
- Game streams
- Music/live-event streams
- Member-only streams
- Any Live Chat where users frequently reuse the same messages or custom emojis

---

## 3. Product Principles

### 3.1 Assist posting; do not automate participation

The extension is a posting aid, not an auto-chat tool.

v1.0 must not implement:

- Periodic automatic posting
- Automatic posting when a stream starts
- Conditional or event-triggered posting
- Bulk posting
- Multi-stream simultaneous posting
- Automatic retry after an ambiguous send result

Every actual post must ultimately originate from an explicit user action.

### 3.2 Use YouTube's native chat behavior

The extension must rely on YouTube's own chat input and posting behavior whenever possible.

YouTube remains responsible for:

- Authentication state
- Membership eligibility
- Whether a custom emoji is currently usable
- Chat availability
- Slow mode
- Subscriber/member-only chat restrictions
- Rate limits and other posting restrictions

The extension must not attempt to reproduce or bypass these checks.

### 3.3 Fail closed

When the extension cannot confidently identify the required YouTube UI, it must stop the operation rather than guess.

Example:

```text
Chat input not found
  -> do not insert or send
  -> show an unsupported/currently unavailable state
```

Incorrect DOM interaction is considered worse than temporary feature unavailability.

### 3.4 Isolate YouTube-specific behavior

YouTube DOM selectors and interaction logic must be contained in dedicated adapter classes.

```text
UI
  -> Application Services
      -> YouTube Adapters
          -> YouTube DOM
```

Feature/UI components must not scatter direct YouTube selectors throughout the codebase.

### 3.5 Preserve user drafts

The extension must never silently destroy or clear text already entered by the user.

If an insertion or send operation fails, the draft must remain available whenever technically possible.

## 6. Core UX

The extension mounts a compact panel near the native YouTube Live Chat input.

Example:

```text
+--------------------------------+
| ★ Emojis    💬 Presets      ⚙  |
+--------------------------------+
| [emoji] [emoji] [emoji]        |
|                                |
| [Cute!]                        |
| [That was amazing!]            |
| [Thanks for the stream!]       |
+--------------------------------+

+--------------------------------+
| YouTube chat input...          |
+--------------------------------+
```

The extension should visually integrate with YouTube without replacing or heavily rearranging the native chat UI.

### 6.1 Tabs

Two primary tabs are provided:

- Favorite Emojis
- Message Presets

The last selected tab is persisted.

### 6.2 Collapse behavior

The palette can be collapsed.

```text
[ Live Chat Palette ▲ ]

-> collapsed

[ Live Chat Palette ▼ ]
```

Persist:

```ts
collapsed: boolean;
```

### 6.3 Empty states

The palette must remain understandable and useful even when no presets or favorite emojis have been configured.

Preset empty state:

```text
No message presets yet.
[ + Add preset ]
```

Emoji empty state:

```text
No favorite emojis yet.
Open or refresh YouTube's emoji picker to discover available custom emojis.
[ Refresh emojis ]
```

A completely blank panel is not acceptable.

The empty state must provide the next actionable step without forcing the user to open the extension options page unless necessary.

## 7. Message Presets

### 7.1 Data model

```ts
interface MessagePreset {
  id: string;
  text: string;
  scope: "global" | "channel";
  channelId?: string;
  order: number;
  createdAt: number;
  updatedAt: number;
}
```

### 7.2 Global presets

Global presets are visible on every supported Live Chat.

Examples:

```text
LOL
Cute!
Amazing!
Thanks for the stream!
```

### 7.3 Channel presets

Channel presets are visible only for the matching YouTube channel.

The stable YouTube `channelId` must be used as the logical channel key. Display names must not be used as identifiers.

## 8. Preset Click Behavior

### 8.1 Default click

Normal click inserts the preset into the YouTube input field but does not send it.

```text
Preset click
  -> insert into native chat input
  -> user reviews message
  -> user sends normally
```

This is the default behavior.

### 8.2 Explicit instant send

Instant-send for **message presets only** is available but disabled by default.

Setting:

```text
Send immediately when preset is clicked
[ OFF ]  <- default
[ ON  ]
```

When enabled:

```text
Preset click
  -> insert
  -> validate send availability
  -> trigger native send
```

### 8.3 Modifier send

Even when instant-send is disabled:

- `Ctrl + Click` on Windows/Linux
- `Command + Click` on macOS

performs an explicit immediate send for **message presets only**.

Therefore the safe default preset interaction is:

```text
Click              -> insert only
Cmd/Ctrl + Click   -> insert and send
```

### 8.4 Emoji clicks never send immediately

Favorite emoji interaction is intentionally different from preset interaction.

```text
Emoji click              -> insert only
Cmd/Ctrl + Emoji click   -> insert only
```

There is no instant-send setting or modifier-based immediate send for custom emojis in v1.0.

Rationale:

- Users often combine multiple emojis before posting.
- Users often combine an emoji with text.
- Immediate emoji posting creates a disproportionately high accidental-post risk.

## 9. Chat Input Adapter

Direct assignment such as the following is prohibited:

```ts
element.innerHTML = text;
```

YouTube's own editable input state must be respected.

Provide a dedicated adapter:

```ts
interface ChatInputAdapter {
  findInput(): HTMLElement | null;
  readDraft(): string;
  insertText(text: string): Result<void>;
  send(): Result<void>;
  isSendEnabled(): boolean;
}
```

Expected insertion flow:

```text
focus
  -> determine current selection/caret
  -> insert or replace selected text
  -> dispatch the appropriate input event
  -> verify YouTube's input state changed
```

If insertion success cannot be confirmed, an immediate send must not occur.

### 9.1 Preserve existing draft text

Existing user text must never be silently replaced as a whole.

Presets are inserted at the current caret position whenever possible.

### 9.2 No automatic whitespace

The extension must not automatically add spaces before or after a preset.

Insertion is semantically:

```text
beforeSelection + presetText + afterSelection
```

This is important for languages such as Japanese where automatic whitespace is often undesirable.

Users who want leading or trailing whitespace may include it in the preset itself.

### 9.3 Selection replacement

If the user currently has a text selection inside the chat editor, inserting a preset replaces the selected range.

Example:

```text
Before:
This is [great] today

Selected:
great

Preset:
amazing

After:
This is amazing today
```

If there is no active selection, insertion occurs at the caret position.

### 9.4 Caret restoration

After insertion, the caret should be placed immediately after the newly inserted preset/emoji whenever YouTube's editor model allows this reliably.

This enables repeated composition such as:

```text
[preset] -> [emoji] -> [emoji] -> manual text
```

without requiring the user to re-focus the native input.

## 10. Send Behavior and Failure Handling

### 10.1 Native send only

All send actions must use YouTube's current native send behavior/control.

Do not emulate YouTube network requests.

### 10.2 Pre-send validation

Before a preset immediate-send operation:

```text
confirm insertion succeeded
  -> confirm native send appears enabled
  -> trigger native send once
```

If either condition cannot be confirmed, do not send.

### 10.3 No automatic retry

A send operation must never be automatically retried.

This avoids duplicate comments when the extension cannot determine whether YouTube accepted the first action.

### 10.4 Preserve draft on failure

If a send attempt fails or its result is ambiguous:

```text
send attempt
  -> failure / uncertain result
  -> do not clear the editor
  -> do not retry
  -> show a lightweight error state
```

The extension must not intentionally clear the draft after a failed send.

If YouTube itself mutates the editor unexpectedly, the extension must not try to reconstruct content by guessing.

### 10.5 Do not over-classify YouTube chat restrictions

v1.0 does not need to independently distinguish every reason a message cannot be sent.

Examples include:

- Slow mode
- Member-only chat
- Subscriber-only chat
- Account restrictions
- Temporary posting restrictions
- YouTube-side UI changes

The extension may expose broad states such as:

```text
Ready
Posting unavailable
Unable to determine chat state
```

YouTube remains the authority for the specific restriction and user-facing native explanation.

### 10.6 Send lock

After triggering a send, temporarily disable extension-originated send actions for a short interval to reduce accidental double activation.

Recommended initial value:

```text
800 ms
```

This is only a local double-activation guard and must not attempt to replace YouTube slow-mode or rate-limit behavior.

## 11. Custom Emoji Support

In this document, "custom emoji" refers to YouTube's channel-provided custom/member emojis.

The extension must not fabricate an emoji representation and inject an arbitrary image into the chat editor.

The preferred flow is:

```text
Live Chat Palette favorite
  -> EmojiAdapter
      -> resolve current native YouTube emoji
          -> native emoji insertion
              -> native chat input
```

This ensures YouTube remains the authority over whether the emoji is actually available to the current account.

---

## 12. Emoji Adapter

```ts
interface EmojiAdapter {
  openPicker(): Promise<Result<void>>;
  closePicker(): Promise<void>;
  scanAvailableEmojis(): Promise<Result<AvailableEmoji[]>>;
  resolveEmoji(ref: EmojiReference): Promise<Result<ResolvedEmoji>>;
  insertEmoji(emoji: EmojiReference): Promise<Result<void>>;
}
```

### 12.1 Discovery

Custom emojis should be discovered from the native YouTube emoji UI available to the current user.

Do not use a membership API or infer eligibility independently.

Basic flow:

```text
Refresh emojis
  -> access native YouTube emoji picker
  -> inspect currently available emojis
  -> identify custom/channel emojis
  -> update local palette metadata
```

### 12.2 Emoji reference model

Persistent favorites must not use an image URL or a transient DOM identifier as the logical identity.

Use:

```ts
interface EmojiReference {
  id: string;
  channelId: string;
  familyName: string;
  emojiName: string;
  displayName: string;
  imageUrl?: string;
  lastSeenAt: number;
}
```

Logical identity:

```text
channelId + familyName + emojiName
```

Reasoning:

- `imageUrl` may change and is therefore cache/display metadata only.
- A transient DOM/internal identifier may change when YouTube changes implementation details.
- `familyName` is not assumed to be globally unique.
- `emojiName` is not assumed to be globally unique across all channels/families.
- Including `channelId` prevents cross-channel collisions.

The persisted `id` may be a generated UUID for storage operations, but equality/re-resolution semantics must be based on the logical identity above.

### 12.3 Resolve before insertion

A stored favorite is only a reference to an emoji last observed in YouTube's UI.

When the user clicks a favorite:

```text
stored EmojiReference
  -> inspect/resolve against currently available native emojis
  -> exact logical match found
      -> invoke native insertion
  -> exact logical match not found
      -> fail closed / mark unavailable
```

Do not inject a cached emoji image into the input as a fallback.

### 12.4 Unavailable emoji

If a previously favorited emoji is not currently available, disable it instead of attempting to send or fabricate it.

```text
[emoji 🔒]
Currently unavailable
```

Possible causes do not need to be distinguished in v1.0. They may include:

- Membership status changed
- Emoji removed or renamed
- Different channel context
- YouTube UI changed

### 12.5 Emoji refresh

Provide an explicit action:

```text
↻ Refresh emojis
```

Attempt refresh on:

- First palette load for a channel
- Channel context change
- Full page reload

However, automatic synchronization must not visibly open or disrupt the user's native emoji picker. If native UI interaction would be intrusive, require the explicit refresh action.

## 13. Channel and Video Context

```ts
interface VideoContext {
  videoId?: string;
  channelId?: string;
  channelName?: string;
}
```

Use a dedicated adapter:

```ts
interface WatchContextAdapter {
  detectVideoId(): string | null;
  detectChannelId(): string | null;
  detectChannelName(): string | null;
}
```

DOM-based detection details must remain inside this adapter.

If `channelId` cannot be resolved, global presets may remain available, but channel-specific features must fail closed.

---

## 14. YouTube SPA Navigation

YouTube commonly changes videos without a full page reload.

The extension must not assume a single initialization per document lifetime.

Observe relevant navigation/context changes:

```text
Navigation change
DOM change
Video context change
```

On context change:

```text
old context
  -> invalidate channel-specific state
  -> detect new context
  -> load matching presets
  -> re-evaluate emoji availability
```

Avoid reacting to every arbitrary DOM mutation as a full navigation event.

---

## 15. iframe Handling

Live Chat may run inside an iframe. Content scripts should be configured to support matching frames where necessary.

Example concept:

```json
{
  "content_scripts": [
    {
      "matches": ["https://www.youtube.com/*"],
      "all_frames": true
    }
  ]
}
```

Each injected script must determine whether it is running in:

- Main watch-page frame
- Live Chat frame
- Irrelevant YouTube frame

and initialize only the responsibility appropriate for that context.

## 16. Architecture

```text
YouTube Watch Page
       |
       | VideoContext
       v
Watch Content Script
       |
       v
Service Worker
       |
       | Context / messaging
       v
Live Chat Content Script
       |
       v
Live Chat Palette UI
       |
       +---- PresetService
       |
       +---- EmojiService
                  |
                  v
            YouTube Adapters
                  |
                  v
              YouTube DOM
```

### 16.1 WatchContentScript

Responsibilities:

- Detect supported YouTube page context
- Detect `videoId`
- Detect `channelId`
- Detect SPA navigation/context changes
- Publish context updates

### 16.2 ChatContentScript

Responsibilities:

- Determine whether current frame is Live Chat
- Mount the palette
- Detect destructive/reconstructive chat DOM changes
- Restore the extension UI if YouTube rebuilds its surrounding DOM

### 16.3 ServiceWorker

Responsibilities:

- Route messages between frames
- Share current video/channel context
- Coordinate session state
- Access extension storage when appropriate

The service worker must not access DOM APIs.

The design must not assume that a Manifest V3 service worker remains permanently alive.

### 16.4 LiveChatPalette UI

Responsibilities:

- Tabs
- Favorite emojis
- Presets
- Collapse/expand
- Empty states
- Error/unavailable states
- Link to settings/options

### 16.5 YouTube adapters

Responsibilities:

- Locate native chat input
- Insert/replace text while preserving draft content
- Detect/send via the native send control
- Discover native custom emojis
- Re-resolve stored emoji references
- Trigger native emoji insertion
- Resolve watch/channel context

## 17. Storage

Use:

```text
chrome.storage.local
chrome.storage.session
```

### 17.1 `chrome.storage.local`

Persistent user data:

- Message presets
- Favorite emoji references
- UI preferences
- Known channel metadata

### 17.2 `chrome.storage.session`

Temporary browser-session state:

- `tabId`
- `videoId`
- `channelId`
- `channelName`

Do not rely solely on service-worker global variables for recoverable state.

### 17.3 Schema

```ts
interface StorageSchema {
  schemaVersion: 1;

  settings: {
    presetInstantSend: boolean;
    collapsed: boolean;
    lastSelectedTab: "emoji" | "preset";
  };

  presets: MessagePreset[];
  favoriteEmojis: EmojiReference[];

  channels: Record<
    string,
    {
      channelId: string;
      channelName?: string;
      lastSeenAt: number;
    }
  >;
}
```

The setting is named `presetInstantSend` rather than a generic `instantSend` because emoji actions never support immediate send in v1.0.

### 17.4 Schema migration

Persist a schema version from the first release:

```ts
schemaVersion: 1;
```

All future storage changes must support explicit migrations such as:

```text
1 -> 2
2 -> 3
```

## 18. Extension Permissions

Keep permissions minimal.

Expected core permission:

```json
{
  "permissions": ["storage"]
}
```

Expected host scope:

```json
{
  "host_permissions": ["https://www.youtube.com/*"]
}
```

The final implementation should verify whether host permissions can be narrowed further without harming Live Chat support.

Do not request these unless a later implementation proves them necessary:

- `tabs`
- `history`
- `cookies`
- `identity`
- `webRequest`
- `downloads`
- `clipboardRead`
- `clipboardWrite`

No permission should be added solely because it might be useful in a future version.

## 19. Authentication and Network Policy

v1.0 uses no Google OAuth.

The extension must not require access to Google account credentials or tokens.

v1.0 also has no proprietary backend and no telemetry endpoint.

Expected data flow:

```text
Extension
  +-- YouTube DOM/native UI
  +-- Chrome extension storage
```

No user preset/comment data is sent to an extension-owned external server.

## 20. Privacy

Do not collect:

- Google account details
- YouTube account details
- Browsing history
- Comment history
- Membership history
- Posted message contents
- Usage analytics

User-created presets and extension preferences are stored locally.

## 21. UI Isolation

Use a Shadow DOM root for extension UI where practical.

```text
Extension mount
  -> ShadowRoot
      -> Live Chat Palette
```

Do not rely on YouTube CSS classes for the extension's own visual styling.

Support both light and dark environments using extension-owned theme variables and platform primitives such as `color-scheme` where appropriate.

---

## 22. DOM Reconstruction and Mount Safety

YouTube may reconstruct portions of the Live Chat DOM during navigation or state changes.

Use a scoped `MutationObserver` to detect removal of the extension mount point or relevant native controls.

Do not observe the entire YouTube document with expensive processing on every mutation.

Use a mount guard such as:

```html
<div data-live-chat-palette-root="true"></div>
```

Before mounting, verify that another extension root is not already present.

If YouTube removes the root:

```text
relevant DOM mutation
  -> debounce
  -> verify chat context still valid
  -> verify root missing
  -> mount once
```

Recommended initial debounce window:

```text
100–300 ms
```

---

## 23. Selector Strategy

Selectors must be centralized inside YouTube adapters.

Bad:

```ts
document.querySelector("yt-live-chat-...");
```

scattered across UI and services.

Preferred:

```text
youtube/
  ChatInputAdapter
  EmojiPickerAdapter
  SendButtonAdapter
  WatchContextAdapter
  selectors
```

Adapters may use a small ordered strategy list where justified:

```text
Strategy A
  -> fail
Strategy B
  -> fail
Strategy C
  -> fail
Unsupported
```

Fallback selectors must still be specific and semantically verified.

Never click a merely "similar-looking" element.

## 24. Error States

Use a small set of user-facing states instead of exposing internal selector/debug details.

### Chat unsupported

```text
YouTube's chat input could not be recognized.
```

### Emoji unsupported

```text
Custom emojis are currently unavailable.
```

### Channel unknown

```text
Channel information could not be determined.
Global presets remain available.
```

### Send failed

```text
The comment could not be sent.
Your draft has been kept when possible.
```

### Emoji unavailable

```text
This favorite emoji is not currently available.
```

Production UI must not expose raw DOM selectors, stack traces, or internal adapter errors.

## 30. Message Protocol

Frame communication must use typed messages rather than free-form string conventions scattered across the codebase.

Example:

```ts
type ExtensionMessage =
  | {
      type: "CONTEXT_UPDATED";
      context: VideoContext;
    }
  | {
      type: "GET_CONTEXT";
    }
  | {
      type: "CONTEXT_RESPONSE";
      context: VideoContext | null;
    };
```

## 31. Popup Live Chat

Popup Live Chat is best-effort in v1.0.

If sufficient channel context can be resolved from the popup page or session context, channel features may be enabled.

If the channel cannot be safely resolved:

- Global presets may remain available.
- Channel-specific presets remain disabled.
- Emoji discovery may be offered if the native picker itself provides enough context.
- Do not guess the channel from display text alone.

Complex popup-specific context reconstruction is outside v1.0.

## 44. Implementation Notes (v1.0)

These are the deliberate, minor deviations made while implementing v1.0. None change the product
scope or the safety guarantees above.

### 44.1 Content script injection

Rather than a single `all_frames` content script on `https://www.youtube.com/*` (§15), two narrower
declarations are used:

- a watch-context script on `https://www.youtube.com/*` that initializes only in the top watch
  frame; and
- a chat script on `https://www.youtube.com/live_chat*` with `all_frames: true`.

Each still verifies its frame role at runtime (`watch` / `chat` / `irrelevant`) and initializes only
its own responsibility. This narrows where code runs while preserving iframe and popup-chat support.

### 44.2 Host permissions

`host_permissions` is intentionally empty. The `content_scripts` `matches` on
`https://www.youtube.com/*` are sufficient for all v1.0 functionality (DOM assistance only, no
`fetch`/`scripting` into the page), so no separate host permission is requested. Package validation
fails if `host_permissions` is non-empty.

### 44.3 Reordering

v1.0 ships accessible move-up / move-down controls in the options page (satisfying §26's requirement
that ordering not depend on drag-and-drop and that explicit order metadata be stored). Drag-and-drop
remains a possible future enhancement; the storage model already carries explicit `order`.

### 44.4 Emoji identity key

The logical identity (`channelId + familyName + emojiName`, §12.2) is compared field-by-field. Where
a single string key is needed (UI `data-*`, de-duplication) the fields are joined with the U+001F
unit-separator, which cannot occur in the source fields. `imageUrl` is never part of identity.

### 44.5 Popup live chat

Popup live chat mounts and offers global presets and native-picker emoji discovery, but channel
presets and channel emoji favorites stay disabled unless the channel is resolved for that tab. The
video id alone is never used to guess a channel (§31 best-effort / fail closed).

### 44.6 Channel id detection on real watch pages

Real watch pages (verified against a hololive live page) usually expose only a `/@handle` in the
owner block and author microdata, and omit `<meta itemprop="channelId">`, so a channelId must come
from elsewhere. Detection order is:

1. `/channel/UC…` link in the video owner block (live; updates on SPA navigation)
2. `ytInitialPlayerResponse.videoDetails.channelId`, read from the inline `<script>` text — the
   authoritative id YouTube embeds for the player
3. schema.org author microdata channel URL
4. `<meta itemprop="channelId">`

Strategies 2–4 are trusted only while their own video id equals the current URL's video id, so a
stale (SPA-navigated) inline script is ignored rather than trusted. A page-wide scan for
`/channel/UC…` anchors is deliberately NOT used: a watch page contains links to other channels
(recommendations, description), so it is ambiguous. When none of the strategies yield a single
unambiguous id, channel features stay disabled (fail closed) and global presets remain available;
a full page reload repopulates the inline player response and typically resolves the channel.

### 44.7 Emoji-aware presets

Member/custom emojis are `:_shortcode:` text that YouTube renders as images. Two usability issues
followed: copy-pasting an emoji into the preset text field does not yield the shortcode (it is an
image), and a preset shown as raw `:_shortcode:` text is unidentifiable. Since emoji discovery
already captures each emoji's `emojiName` (the shortcode) + `imageUrl`, the palette now:

- renders known `:_shortcode:` occurrences as inline images in preset chips and a live form preview
  (channel-scoped lookup against discovered emojis; unknown/undiscovered shortcodes stay as text);
- lets the user append a shortcode by clicking a discovered emoji in the preset form (no copy-paste).

Insertion is unchanged: the preset text (including shortcodes) is inserted and YouTube converts the
member shortcodes to images natively on send. No image is ever fabricated into the chat editor.

### 44.8 Emoji picker DOM (verified against a real live stream)

Inspected against a real hololive live chat (Oozora Subaru). The earlier assumed selectors were
wrong; the verified facts are:

- Picker container: `yt-emoji-picker-renderer` (id is also `emoji`, so `#emoji` alone is ambiguous).
- Categories: `yt-emoji-picker-category-renderer`, each with a `#title` and an `#emoji` listbox.
- The **member/custom** listbox has class `CATEGORY_TYPE_CUSTOM`; YouTube's global animated emojis
  are `CATEGORY_TYPE_GLOBAL`; unicode emojis `CATEGORY_TYPE_UNICODE_EMOJI`. Custom detection keys off
  `CATEGORY_TYPE_CUSTOM` (global/unicode are excluded).
- Picker `<img>` elements have **no `emoji` class** (that class only appears on the node inserted
  into the editor). They carry `role="option"`, `aria-label=":_shortcode:"` (the typeable shortcode),
  `alt="display name"`, and `id="<channelId>/<hash>"` (not `data-emoji-id`).
- So `emojiName` = aria-label shortcode, `displayName` = alt. The previous `img.emoji` selector
  matched nothing, which is why the Emojis tab reported "no custom emojis" even with the picker open.

Virtualization caveat: the picker only fully materializes its emoji `<img>` nodes while it is
actually visible on screen. When it is not painted (e.g. headless automation), YouTube renders only
a placeholder image per category. Discovery therefore requires the native picker to be open and
visible, which is the documented refresh flow; the exhaustive-count behavior can only be confirmed
by a real manual check (a member account with the picker open).

### 44.9 Multi-emoji preset insertion (verified on a real live stream)

A preset containing several `:_shortcode:` tokens must convert every one to its emoji image. Verified
behavior of YouTube's chat input:

- Inserting the whole preset string in ONE `execCommand('insertText')` converts only the LAST
  shortcode (the one at the caret) — the earlier ones stay as literal text. (This was the reported
  bug, and it also broke insertion verification, since the converted emoji no longer equals the
  literal text, producing a false "could not insert" error.)
- Inserting each token (text run or `:_shortcode:`) in its OWN `execCommand` call, spaced out by a
  short delay, converts every shortcode — with no extra spaces added.

So `ChatActionService` composes a preset: plain text is one strict, exact insertion; text containing
shortcodes is split into segments and inserted one at a time (`ChatInputAdapter.insertChunk`, which
verifies only that the editor changed, tolerating the shortcode→image conversion) with a delay
between segments (`DEFAULT_CHUNK_DELAY_MS`). No emoji image is fabricated or injected — YouTube
performs each conversion natively.
